From Text to Tokens: How LLMs Read Language

Follow a message from characters to vocabulary entries, then calculate what those choices cost in context, memory, and engineering complexity.

Prerequisite: basic arithmetic; chapters 01-02 provide connections13 sectionsOriginal diagrams + fully worked algorithms

The question we are answering

Your application sends a short message, yet the API reports many tokens. What exactly did the model receive, and why does the answer depend on the tokenizer?

Your application starts with text, but a language model needs numbers. A tokenizer connects the two. It splits text into pieces and gives each piece a numerical ID from a fixed vocabulary. It follows rules about the text and the available pieces; it does not need to understand the sentence first.

The word "read" in this chapter's title means this input conversion, not human comprehension. We will build small tokenizers you can trace with a pencil, distinguish their assumptions from real implementations, and connect their output to the matrices and learning machinery of the earlier chapters. No probability or Unicode knowledge is assumed.

How to work through this chapter

First learn the units and lookup contract in sections 1-2, then trace the three algorithms in sections 3-7. Sections 8-11 connect them to model storage and application requests. In section 6, understand the three-path example before continuing into the more demanding dynamic-programming, logarithm, and estimation calculations; they explain implementation choices, not prerequisites for recognizing a token. Each section has an explained check so you can test your reasoning before moving on.

1. Text, characters, bytes, and tokens are different units

Imagine storing the customer message Send maps.. A word is a linguistic unit; spaces and punctuation help a human recognize words in this English example. But spaces are not universal word boundaries. Chinese text, source code, email addresses, and product identifiers all challenge a simple "split on spaces" rule.

In software, "one character" can mean different things. What looks like one character on screen may contain several text elements. This visible unit is called a grapheme cluster. Unicode gives text elements numbered addresses called code points. For example, U+0041 is capital A. The part after U+ uses base sixteen: after digits 0 through 9, it uses A through F. A code point identifies a text element; it is not a byte.

A bit is either 0 or 1. A byte contains eight bits. Each bit has two choices, so a byte has 2^8=2\times2\times2\times2\times2\times2\times2\times2=256 possible patterns, numbered 0 through 255. The exponent 8 means multiply eight factors of 2.

A text encoding turns code points into bytes for storage or transmission. UTF-8 uses one to four bytes for each permitted Unicode code point. There is one boundary worth knowing: Unicode reserves numbers called surrogates for UTF-16's internal encoding rules. A surrogate on its own is not a valid UTF-8 text character.

For example, Unicode NFC normalization combines this e-plus-accent into the precomposed form. A tokenizer may normalize, lowercase, or preserve text; its configuration decides. Worked example / Count the unit you mean

For Aé using precomposed é, there are two code points and 1+2=3 UTF-8 bytes: [65, 195, 169]. A raw byte tokenizer would emit three ordinary tokens. A toy vocabulary containing the entire byte sequence for Aé could instead emit one token. Neither count is a count of English words. In JavaScript, string.length counts UTF-16 code units, another storage unit; do not assume it counts graphemes, Unicode code points, UTF-8 bytes, or model tokens.

A token is one unit recognized by a particular tokenizer. Ordinary text tokens can cover a whole word, part of a word, punctuation, whitespace, or several of these together. Byte tokens can even cover less than a complete Unicode character. Special tokens, introduced in section 9, represent structure rather than ordinary text.

Predict / Same appearance, same count?

Without normalization, must the two accent spellings above produce the same tokens? What changes if both are normalized to NFC first?

Reveal solution

No. Their byte inputs differ, so a byte-based tokenizer can produce different IDs and counts. NFC makes these particular inputs identical before segmentation, so a deterministic tokenizer with the same configuration then produces the same result. Decoding cannot tell which original spelling was used after that distinction has been removed.

2. A vocabulary is a contract, not a dictionary of meanings

A vocabulary is the finite collection of token entries available to the tokenizer. A token ID is an integer identifying one entry. A sequence is an ordered list: [7, 3] is different from [3, 7]. Order matters because map followed by s spells something different from s followed by map.

Segmentation means choosing the ordered pieces that cover an input. In our displays, map | s means two tokens, not text containing a vertical bar or an inserted space. Similarly, m a p shows three character tokens from map; the separating spaces are diagram notation. Literal spaces in input will be called out explicitly. A saved tokenizer artifact contains its vocabulary and the rules and settings needed to repeat its behavior.

With the segmentation ["map", "s"], encoding maps maps to [7, 3]. Decoding looks up the entries and reconstructs maps. ID 7 is not seven units of meaning. Its distance from ID 3 does not measure similarity. Renumbering this vocabulary is safe only if all dependent model rows, output classes, and special-token settings are updated consistently.

The ID tells the model which stored numbers to retrieve. Those numbers form an embedding: an ordered list, also called a vector. Each value in that list is a coordinate. An embedding matrix stores these lists in a rectangular table, one row per ID and one column per coordinate. Each stored number is a model parameter, or weight, that training can adjust. The model's Transformer layers then process the retrieved vectors. You do not need to know their internal design to follow a row lookup.

Why not store every word? A word-only dictionary must handle new names, typos, code, and word variations; an unseen word may become an out-of-vocabulary item, abbreviated OOV. A character-level system reuses smaller pieces but usually needs longer sequences, and a finite character inventory can still miss a character. A subword system reuses pieces smaller than words while retaining larger common units. A piece is not guaranteed to be a grammatical root or suffix.

A compiler lexer is a useful analogy: both turn text into units. But a programming-language lexer recognizes a specified grammar, whereas many LLM tokenizers learn reusable units from a corpus, a collection of training text. Neither operation alone is semantic understanding.

Do not confuse three different activities

Tokenizer training builds the vocabulary and splitting rules from a corpus. Once saved, these rules can be reused. Encoding and decoding use that saved tokenizer; a new user message normally does not change it.

Model training is a separate job. It adjusts the model's stored numbers, including embedding values, to improve predictions. During ordinary generation, neither the tokenizer nor the model weights change. The model chooses new output tokens using what has already been trained.

Worked example / The simplest lookup into a model

Suppose a toy embedding table has eight rows, one per ID above, and three numbers per row. The sequence [7, 3] selects row 7, [0.2, -0.5, 0.8], followed by row 3, [0.6, 0.1, -0.2]. The resulting input has two rows and three columns. You do not multiply all numbers by 7 or 3. Chapter 1's matrix operations act on the retrieved values; chapter 2's training updates those values.

Tokenizer decoding turns IDs back into text; it does not choose a reply. During inference, the model uses its trained weights to predict possible next IDs. A generation procedure chooses one, appends it, and repeats. If it chooses ID 7 and then ID 3, our tokenizer renders maps. The model and generation procedure chose the IDs; the tokenizer only decoded them.

Serving documentation sometimes calls this repeated generation phase "decode" too. Check whether the term means choosing new IDs or turning existing IDs into text.

Predict / New spelling or new training?

The tokenizer has map, l, and e but no whole maple entry. Must an application train a new tokenizer to encode it?

Reveal solution

No, provided its encoding rules can produce map | l | e. Whole-word novelty does not imply failure when the underlying pieces exist. This says nothing about an unseen character outside the base vocabulary; that needs a defined fallback or an explicit failure.

3. BPE training: count, merge, recount

Imagine a log compressor that repeatedly notices the same adjacent fragments. Replacing two fragments with one saves one sequence position at each non-overlapping occurrence. Byte Pair Encoding, or BPE, began as a compression method; tokenizer training adapts the pair-merging idea to build reusable units. Despite the historical name, our first example starts with characters, not bytes.

Adjacent means immediately next to each other in the current sequence. A pair's frequency is its occurrence count, including repeated corpus entries. A merge replaces a selected adjacent pair with one combined token. The new entry is added to the vocabulary; old entries remain usable. A merge rank records its order in training, with a smaller rank meaning an earlier merge.

Exact assumptions for this teaching tokenizer

Our entire corpus is map four times, maps twice, and maple once. We process entries in that order. We start with the six characters m, a, p, s, l, e; there are no boundary tokens or special tokens. Pairs never cross entry boundaries. On equal frequency, select the pair first encountered while scanning these entries from left to right. Replace non-overlapping occurrences from left to right. Stop after five merges. These deterministic rules make this example reproducible; they are not a specification for every BPE library.

We can store each unique entry once with its frequency. This is equivalent to repeating it in the corpus. To count a pair, count occurrences within each entry, multiply by that entry's frequency, and add. For example, (m,a) appears once in each entry, so its total is 1(4)+1(2)+1(1)=7. The parentheses here group arithmetic factors; in (m,a) they denote an ordered pair of tokens.

Worked example / Every merge and every intermediate corpus

Rank 1. The top count 7 is tied. Our scan sees (m,a) first, so merge it into ma. The entries become ma p (4), ma p s (2), and ma p l e (1). Recount: (ma,p):7, (p,s):2, (p,l):1, (l,e):1.

Rank 2. Merge (ma,p) into map. The entries become map (4), map s (2), and map l e (1). Recount: (map,s):2, (map,l):1, (l,e):1. A one-token entry has no adjacent pairs.

Rank 3. Merge (map,s) into maps. The entries become map (4), maps (2), and map l e (1). Recount: (map,l):1, (l,e):1.

Rank 4. The counts tie again; our scan reaches (map,l) first. Merge it into mapl. The entries become map (4), maps (2), and mapl e (1). Only (mapl,e):1 remains.

Rank 5. Merge (mapl,e) into maple. The entries become map (4), maps (2), and maple (1). No pair remains. We reached the merge limit and would also stop because no further merge is possible.

The final vocabulary is {m, a, p, s, l, e, ma, map, maps, mapl, maple}. A token such as mapl has no special linguistic meaning. It exists because of the counts and tie-breaking rule, not because the algorithm discovered a meaningful word part, called a morpheme.

Overlaps make "count" different from "replace"

For a a a, the pair (a,a) occurs at positions 1-2 and 2-3, so its adjacent-pair count is 2. But replacing the first pair consumes the middle a. A left-to-right non-overlapping replacement yields aa a, not two aa tokens. That is one actual replacement and one position saved. Libraries can differ in training details; do not assume pair count always equals immediate token savings when pairs overlap.

LLM connection. Production tokenizer training uses vastly larger corpora, targets, and implementation machinery. The enduring mechanism is to count the current units, add a merged entry, and update the representation. A vocabulary target must leave room for base and special entries; training may stop early if no useful pair remains.

Predict / A tempting but wrong recount

Immediately after rank 2, should (a,p) still have count 7? What happens if the frequency of maps rises from 2 to 5?

Reveal solution

No. The current sequences contain map, not separate a and p tokens. Its old pair is no longer adjacent in the representation. With maps frequency 5, the first two winning pairs each count 4+5+1=10. After those merges, (map,s) counts 5 and still wins rank 3. Counts describe the corpus supplied, not a timeless property of a word.

4. BPE encoding, byte coverage, and decoding

Training saves a vocabulary and an ordered merge list. Encoding uses that list; it does not learn new merges from the user's message. For our toy encoder, start with separate characters. Find neighboring pairs that have a saved merge rule. Apply the rule with the smallest rank, then check the new sequence again. Stop when no saved rule applies. If the chosen pair occurs more than once, replace non-overlapping occurrences from left to right, as in training.

Worked example / Encode using a frozen prefix of the training

Freeze training after rank 2. The available merges are m + a -> ma (rank 1) and ma + p -> map (rank 2). Encoding the previously unseen entry maples follows m a p l e s -> ma p l e s -> map l e s. No listed pair remains. Using section 2's vocabulary, the IDs are [7, 4, 5, 3].

Decode by lookup: ID 7 gives map, 4 gives l, 5 gives e, and 3 gives s. Concatenation, joining without inserting extra text, yields maples. It is a new complete word composed from old entries. If instead we use the final five-merge tokenizer, the same input ends as maple | s. Changing the tokenizer artifact changes the result.

Merge-rank BPE is not generally interchangeable with "take the longest string in the vocabulary." Greedy longest-match is a different encoding rule, used in the WordPiece example below. Record the algorithm as well as the vocabulary. Preprocessing, boundaries, and rank order are all part of a reproducible BPE encoding.

Worked example / Two eligible merges compete

Use a separate toy vocabulary {a, b, c, bc, ab}. Its learned rules are b + c -> bc at rank 1 and a + b -> ab at rank 2. Such rules can result, for example, from a corpus containing bc three times and ab twice. Encode the new input abc, initially a b c.

Both (a,b) and (b,c) are eligible, but rank 1 wins even though its pair is farther right. The sequence becomes a bc. No rule merges a with bc, so the final result is a | bc. Taking the longest vocabulary prefix instead would choose ab and leave c: ab | c. Both spell the input, but only the first follows these BPE ranks. Merge priority, not the current prompt's pair frequency or a leftmost-longest guess, decides this result.

What if a base unit is missing?

The six-character toy cannot losslessly encode mapped: d is missing. It must reject that input or follow an explicit unknown-unit policy. It would be wrong to silently invent d, a new ID, or a new merge. The same issue affects an alphabet trained without a newly encountered script.

Byte-level BPE begins with all 256 byte values, then learns merges over byte sequences. With that complete base vocabulary, any byte sequence can be decomposed into available units, even if no larger learned token matches. UTF-8 gives ordinary valid Unicode text a byte representation. This solves base-byte coverage, not semantic comprehension or equal efficiency across languages.

Byte fallback is a related but distinct configuration: a tokenizer whose normal units are characters or subwords can fall back to byte entries for an uncovered portion. It must actually include and enable those entries. Not every Unigram or SentencePiece tokenizer does. An UNK token instead says "unknown"; once spelling is replaced with it, exact reconstruction is usually impossible.

Worked example / Reconstruct bytes before decoding text

Suppose a byte vocabulary emits separate byte tokens for precomposed é with payloads [195] and [169]. A payload is the byte content stored in an entry; these byte values are not necessarily its token ID. Concatenating the payloads gives [195, 169], a valid UTF-8 encoding of é. Neither byte alone is a complete UTF-8 character. Decoding them independently as text can produce an error or replacement character. During inspection, show raw bytes; during streaming, keep incomplete UTF-8 fragments buffered until the sequence is complete. A model can also generate a byte sequence that is not valid UTF-8, so the decoder's error policy matters.

The surrounding pipeline changes the legal merges

Pre-tokenization divides input into chunks before the subword algorithm runs. A regular expression, a pattern describing classes of text, might separate letter runs, digit runs, or punctuation. Some byte-BPE implementations use such patterns. If map and ! are placed in separate chunks, no BPE merge can cross that boundary even if the combined bytes appear elsewhere in a vocabulary. Other designs do not require word pre-tokenization.

To inspect a tokenizer, follow the text through its steps: normalization, any pre-tokenization, conversion to base units, segmentation, ID mapping, and special-token processing. A library may arrange or combine these steps differently, so check its configuration.

Then test the round trip: encode text and decode the IDs. A lossless configuration should return the original text. If normalization or UNK removed information, decoding can return only what remains. Do not assume every tokenizer is reversible.

Predict / Bytes versus understanding

A byte-level tokenizer can encode a new company name written in an unfamiliar script. Does this prove the model understands it? Does adding that name to one prompt add a permanent token?

Reveal solution

Neither. Byte coverage guarantees a representable input, not a learned meaning. It may require many fragmented tokens. Encoding one prompt uses the existing artifact and does not add vocabulary entries or train the model.

5. WordPiece: a vocabulary and a greedy search

BPE training grows a vocabulary by merging frequent neighboring pairs. WordPiece, used by BERT-style models, also builds reusable subword pieces. Its training motivation is to choose a vocabulary that makes the training text more likely under a model.

Here are the two probability terms behind that idea. A probability assigns a number from 0 to 1 to an outcome. For a complete set of mutually exclusive choices, where exactly one is selected, those numbers add to 1. A likelihood asks: how much probability does this model assign to the data we actually observed? Higher likelihood means the data is less surprising under the model, not more factually true. Section 6 works through the arithmetic.

The BERT paper does not fully specify the original WordPiece vocabulary-training procedure. So a likelihood-based motivation is not a complete training recipe, and a tutorial's pair-scoring rule is not necessarily the original rule. Encoding is easier to pin down: once we specify the vocabulary and search rules, we can trace each choice exactly.

Common BERT-style WordPiece encoding works on a pre-tokenized word. At its beginning, find the longest vocabulary prefix matching the remaining text. Then use continuation entries for later pieces. A prefix is text at the beginning: play is a prefix of playing. Greedy means commit to the best local choice now, without exploring all later alternatives.

A complete toy WordPiece vocabulary for this example

The ## prefix marks a continuation entry: a piece allowed inside a word. It is part of the displayed entry name, not letters to insert into the user's text. Beginning entries and continuation entries are different vocabulary items. This toy has no automatic byte fallback, lowercasing, length limit, or extra preprocessing.

Worked example / Trace longest-match-first

Encode playing. Start by testing the whole remaining string playing, then successively shorter prefixes playin, playi, and play. The first vocabulary match is play; consume its four letters. The remaining text is ing. Because we are inside the word, test ##ing, which exists. The result is play | ##ing, not p | ....

For player, choose the same start play, then ##er. For playful, choose play, but no continuation matches the remaining ful. In this BERT-style whole-word fallback example the result is [UNK], not a fabricated ##ful, and not a successful prefix with the rest silently dropped.

To decode the toy result play | ##ing, retain play, remove the continuation display prefix from ##ing, and attach ing without a space: playing. A real tokenizer's decoder also handles pre-tokenization boundaries and punctuation rules; stripping every ## from arbitrary input is not a general decoder. An UNK replacement cannot recover the missing word.

Why greedy is not a global search

For a sharper counterexample, use a separate dictionary with start entries a, ab and continuation entries ##bc only. Input abc chooses ab, then fails because ##c is absent. A global search could find a | ##bc, but ordinary greedy longest-match-first does not backtrack to find it. Configuration-dependent unknown handling is therefore part of the algorithm's contract.

LLM connection. WordPiece continuation markers let related spellings reuse pieces, but they do not prove the model has learned morphology, the structure of how words are formed. BERT-style models also use different training tasks and special tokens from many generative models. You cannot replace one tokenizer with another merely because both split words.

Predict / What does the marker mean?

Can ##ing in our toy serve as the first token of input ing? Does a missing continuation imply the word is meaningless?

Reveal solution

No: the toy requires a beginning entry at the first position, and no ing start exists. The failure describes vocabulary coverage and search rules, not meaning. Another configuration could use different rules or fallback entries.

6. Unigram: compare complete segmentation paths

The same text can be split into several valid token sequences. A Unigram language-model tokenizer compares those complete sequences instead of following BPE merge ranks or WordPiece's longest-prefix choices. It gives each token a probability. To score one sequence, multiply the probabilities of its tokens.

"Unigram" means that a token's stored probability does not change with the preceding token. That is a simplifying assumption for this tokenizer's scoring model. It is not how an LLM predicts its next token using context.

Probability, multiplication, and addition from scratch

Think of a probability as a share of a total of 1, assigned to one possible choice. It cannot be negative. For a complete set of mutually exclusive choices, the shares add to 1. A share of 0 means impossible under the model; 1 means certain. A percentage expresses that share out of 100: 0.4=40/100=40\%.

Our complete toy vocabulary is {a, b, ab, ba}. Give those tokens probabilities 0.4, 0.3, 0.2, and 0.1 respectively. Check the total: 0.4+0.3+0.2+0.1=1. These are shares for choosing one token. A sequence of tokens needs a separate calculation.

To see why we multiply, imagine 100 first choices, 20 of which choose ab. If 40% of those continue with a, that route accounts for 0.2(0.4)=0.08, or 8 out of 100. This assumes independent token choices: choosing ab does not change a's probability. To combine alternative routes, add their scores instead. "Take route A or route B" differs from "choose ab and then a." Real language is not independent in this way; it is an assumption of this tokenizer's score.

P(s)=\prod_{i=1}^{k}p(t_i)=p(t_1)p(t_2)\cdots p(t_k)

s is one segmentation, an ordered sequence of k tokens. The positive integer i indexes positions from 1 through k; t with subscript i is the token at position i. Lowercase p gives a token's stored probability; uppercase P gives a path's product score. The capital Greek pi symbol means multiply the indicated terms. We only take logarithms of positive scores below.

Here p(t) means "look up token t's probability," not "multiply p by t." A subscript names a position: t_1 is the first token of the path, not token ID 1.

For aba, the vocabulary allows exactly three paths: ab | a, a | ba, and a | b | a. There is no whole aba token. We leave out beginning/end symbols because we are comparing splits of this fixed text. For now, treat each product as a path score. The three products do not add to 1; later we will divide by their total to get probabilities for choosing among these paths. Without a stopping rule, they also do not define a probability distribution over complete strings of every length.

Worked example / Choose a path and calculate the text likelihood

Path A: ab | a gives 0.2(0.4)=0.08. Path B: a | ba gives 0.4(0.1)=0.04. Path C: a | b | a gives 0.4(0.3)(0.4)=0.12(0.4)=0.048. The best deterministic segmentation is A because 0.08 is the largest product, even though C has a more probable individual first token.

Now ask a different question: how much total score reaches the text aba, regardless of its split? Add all three paths: 0.08+0.04+0.048=0.168. This sum is the text likelihood used in our toy training objective. Encoding chooses the best path, A. Training can use the sum because the text is known but its split is not.

If products tie, our toy chooses fewer tokens first, then alphabetically ordered token lists. A production library may break ties differently.

Avoid repeating the same search

For longer text, explicitly listing all paths is expensive. Dynamic programming stores answers for prefixes so later steps can reuse them. For the best path, store the best product reaching each character boundary; for total likelihood, store the sum of products reaching it. A boundary is a gap before or after a character, numbered by how many characters have been consumed. The empty prefix has score 1 because multiplying by 1 leaves the first token's score unchanged.

Read the final row by asking what the last token could be. It is either a after the prefix ab, or ba after the prefix a. For the summed score, 0.32 already includes both ways to reach ab. Multiplying it by 0.4 therefore extends both paths at once. Add the separate route ending in ba to get 0.168.

For the best path, keep a record of the winning choice at each boundary. The final 0.08 comes from 0.2 at boundary 2, followed by a. That 0.2 comes from the empty prefix, followed by ab. Walking backward finds a then ab; reverse them to recover ab | a. This best-path computation is often called Viterbi decoding.

Why implementations add logarithms

Long paths create a numerical problem. Ten factors of 0.1 already give 0.1^{10}=0.0000000001. Keep multiplying and a computer may round a tiny positive result to zero. This is called underflow. Logarithms let us compare the same paths by adding scores instead.

A natural logarithm, written ln, answers: "What power of e gives this positive number?" Here e\approx2.71828 is a fixed number. Because e^0=1, we have \ln1=0. A negative exponent means a reciprocal: e^{-1}=1/e\approx0.367879. So \ln(e^{-1})=-1 exactly. The decimal value is rounded; the inverse relationship is exact.

For positive numbers, \ln(ab)=\ln a+\ln b, and ln preserves order: the larger positive input has the larger logarithm. Probabilities between zero and one have negative logarithms. A calculator supplies the approximate log values below; you do not need to derive a logarithm algorithm to use them. Negative log reverses the order, making a smaller value a better score.

Why does the product turn into a sum? Exponents with the same base add when you multiply: e^2e^3=e^{2+3}=e^5. The logarithm reverses exponentiation, so the logarithm of that product is 2+3=5. The same relationship extends to positive real inputs. In \ln(ab), a and b are numerical placeholders, not the text token ab from our vocabulary.

-\ln P(s)=-\sum_{i=1}^{k}\ln p(t_i)

The capital Greek sigma means add the k terms, one for each token position i. The leading minus sign negates that sum. Minimizing this negative log-score is equivalent to maximizing the positive product, not to choosing the fewest pieces by itself.

Worked example / Recheck the winner in log space

For A, add the negative logarithms of 0.2 and 0.4:

-\ln0.2-\ln0.4\approx1.609438+0.916291\approx2.525729

Vocabulary training: start large, estimate, prune

BPE starts small and adds pieces. Unigram training starts with many candidate pieces and removes less useful ones. It repeats three jobs: estimate token probabilities, check which pieces help explain the corpus, and prune some pieces. Then it estimates again. Required coverage units are protected according to the configuration.

The objective is the number training tries to improve. In this example, we want a higher summed text likelihood. Equivalently, we want a lower negative log-likelihood: take the natural log of the sum, then negate it. Notice the order. The text objective uses the log of the sum over paths, not just the log of the winning path.

How can we estimate probabilities when we know the text but not its split? Give each possible split a share of the credit. More likely splits receive more credit. Use those shares to count tokens, then update the token probabilities from the counts. Repeating these two steps is called expectation-maximization, or EM. "Expectation" means a probability-weighted average, not a prediction about the future. The next calculation shows one step.

Worked bridge / One small estimation step

Condition on observing aba. Divide each path score by their total 0.168, a process called normalization: A gets 0.08/0.168=10/21, B gets 0.04/0.168=5/21, and C gets 0.048/0.168=6/21. Check: (10+5+6)/21=1. These are probabilities of alternative paths given this text, unlike the unnormalized products.

First, assign fractional counts. Path A has share 10/21 and contains one a, so it contributes 10/21 of an a count. Path B contributes 5/21. Path C contains two a tokens, so it contributes twice its share: 2(6/21). Add them to get a's expected count: 10/21+5/21+2(6/21)=27/21.

Only C contains b, so b receives 6/21. Only A contains ab, giving 10/21; only B contains ba, giving 5/21. The total is (27+6+10+5)/21=48/21. A fractional count is sensible here: we are averaging counts across paths of different lengths, not claiming that a literal token was cut into fractions.

Second, update the probabilities. For this single-example toy, divide each fractional token count by the total count, without adding other counts or constraints. For a, dividing by a fraction means multiplying by its reciprocal:

\frac{27/21}{48/21}=\frac{27}{21}\frac{21}{48}=\frac{27}{48}

The factor 21 cancels because the same nonzero factor appears above and below the fraction. The updated token probabilities are p(a)=27/48=0.5625, p(b)=6/48=0.125, p(ab)=10/48\approx0.208333, and p(ba)=5/48\approx0.104167. They sum to 1. Real training aggregates across a corpus and uses additional implementation rules; this is one estimation step, not a complete trainer or a guarantee of a globally optimal vocabulary.

Now return to the original probabilities to see why some pieces are safer to remove than others. Do not use the updated EM values for this comparison. Remove ab while keeping the original scores fixed. Path A disappears, leaving B and C with total 0.04+0.048=0.088, down from 0.168.

Take minus the natural log of each total. The negative log-likelihood rises from about 1.783791 to 2.430418, an increase of 0.646627. The rise measures the damage under these frozen scores. It is a diagnostic before re-estimation, not a complete pruning rule or a newly normalized token distribution.

Predict / Read the score, not just the symbols

Path C is a | b | a. What does p(t_2) mean here? Why is removing ba less damaging in the frozen comparison, and can you take ln of a zero path score?

Reveal solution

The second position contains b, so p(t_2)=p(b)=0.3; 2 is a position, not an ID or a multiplier. Removing ba loses B's score 0.04, whereas removing ab loses A's 0.08. Their remaining scores are 0.128 and 0.088 respectively, so the former retains more of the text's score. The real-valued logarithm is undefined at zero. A zero-score path is unavailable to best-path selection; log-space algorithms conventionally represent its log-score as negative infinity, below every finite log-score, rather than evaluating ln(0) as an ordinary finite number.

Predict / More probable or fewer tokens?

Why does the three-token path C beat the two-token path B? Is 0.08 already the probability of choosing A when sampling among these paths?

Reveal solution

C has product 0.048, greater than B's 0.04. A shorter sequence does not automatically win when its entries are less probable. No: 0.08 is A's product score. Conditional path sampling first divides by 0.168, giving A probability 10/21\approx47.62\%.

7. SentencePiece is a framework, not a fourth algorithm

SentencePiece is a software framework: it supplies algorithms and the surrounding text-processing tools. It supports both BPE and Unigram, among other options. The name alone therefore does not tell you the algorithm. You still need to check normalization, byte fallback, and special-token settings.

SentencePiece can train from raw sentences without first splitting words at spaces. It commonly displays whitespace with the marker ▁ (U+2581). A piece displayed as ▁map can represent a space followed by map, not an underline typed by the user.

There are two settings to check before interpreting that marker literally. A dummy prefix can add a boundary marker at the start even when the input has no leading space. Normalization can also change repeated spaces. So the marker alone does not guarantee byte-for-byte preservation of the original whitespace.

Worked example / Boundaries are data or configuration

In a toy whitespace-preserving display with no dummy prefix, map maps could be shown as map | ▁map | s. Decoding the middle piece contributes a space and map. If instead we split on spaces and discard them first, we lose the distinction between one space and two unless we record it elsewhere. For text without spaces, such as 你好, neither BPE nor Unigram inherently requires inserting an English-style word boundary. Their surrounding preprocessing decides where segmentation is allowed.

How training coverage changes the token count

A tokenizer can cover a writing system in bytes without having learned efficient larger pieces for it. If a spelling occurs often in the training corpus, its adjacent base units can get more chances to win BPE merges. The same mechanism applies to recurring letters, punctuation, indentation, and code fragments. Frequency is not a guarantee of one particular merge because other pairs compete and preprocessing can block them.

Worked example / Same text and byte coverage, different learned pieces

Compare two hypothetical byte-BPE artifacts, each with all 256 base byte entries, identical preprocessing, no normalization, and no special tokens added. For the input éé, UTF-8 gives [195, 169, 195, 169]. Artifact A has no applicable learned merge, so it emits four byte tokens. Artifact B has learned the single rule [195] + [169] -> [195,169]. It applies at both non-overlapping occurrences, producing two tokens with payload [195,169] each. Neither artifact has a whole-string éé merge.

Both decode to exactly the same two visible letters. B uses two rather than four tokens because its vocabulary contains a reusable byte sequence, not because UTF-8 changed or the model became more intelligent. These counts belong only to the declared toys. Across real languages and code workloads, measure representative data: training coverage can affect fragmentation, cost, and context consumption, but token efficiency alone cannot establish language understanding.

Predict / A misleading benchmark

One tokenizer emits fewer pieces for a German compound than another. Have you proved that its algorithm is better for German, or that its model understands German better?

No. You observed one input under two whole configurations. Vocabulary size, corpus coverage, and preprocessing can explain the difference. Compare representative workloads for efficiency, and evaluate model quality separately. A smaller token count is not a comprehension test.

8. Vocabulary choices become model dimensions

A larger vocabulary can store more long pieces, so some inputs need fewer tokens. The cost is a larger model table: each extra ID needs a row of stored numbers to learn. An embedding is the vector retrieved from that row. Its dimension counts the numbers in the vector, not words or meanings the model understands.

E\in\mathbb{R}^{V\times d},\qquad N=Vd,\qquad M=Vdb

E names the embedding matrix. The membership symbol means E is a matrix of real numbers; its shape is V rows by d columns. V is the model's vocabulary row count, including supported special entries; d is the positive embedding width. N is the number of stored parameters, one per table entry. b is bytes per parameter, and M is total bytes for this table alone. Symbols written next to each other mean multiplication: Vd means V times d, and Vdb multiplies by b as well. The multiplication sign in a shape says rows by columns.

Our mathematical token positions started at 1 in section 6. IDs in these toy tables start at 0. For a dense vocabulary of V rows, valid IDs run from 0 through V-1. The notation E_{j,:} means row j, where j is a valid token ID and the colon selects all columns. Some real artifacts have reserved or non-contiguous IDs; inspect the model's actual row allocation rather than inferring it from a count of displayed ordinary pieces.

Worked example / Lookup, parameters, and units

A toy table with V = 8 and d = 3 has N=8(3)=24 parameters. ID 7 selects its eighth row, E_{7,:}. If each value is stored using 2 bytes, the table uses 24(2)=48 bytes. The arbitrary integer 7 selects values; it is not itself a three-dimensional representation.

For a hypothetical larger model, let V = 64,000, d = 2,048, and b = 2. First, 64{,}000(2{,}000)=128{,}000{,}000 and 64{,}000(48)=3{,}072{,}000. Add them: N=131{,}072{,}000 parameters. Multiply by 2: M=262{,}144{,}000 bytes.

A decimal megabyte (MB) is 1,000,000 bytes, so this is 262{,}144{,}000/1{,}000{,}000=262.144 MB. A binary mebibyte (MiB) is 2^{20}=1{,}048{,}576 bytes, so it is exactly 250 MiB. These are two unit conventions for the same memory, not conflicting estimates.

A parameter is a stored model number. FP16 and BF16 are two floating-point storage formats commonly using two bytes per value; we use only that storage fact here. Actual allocation can include padding, metadata, quantization scales, or different precision. The estimate excludes all other layers, activations, optimizer state, and serving caches.

The vocabulary also affects the output side. To predict the next ID, a model typically calculates one score for every vocabulary entry. If its current hidden vector has d numbers, a separate output weight table needs dV values, plus any configured bias. This is called an untied output projection.

Weight tying reuses the input embedding weights for that output calculation. It avoids storing a second set of weights. The model must still calculate output scores, and the IDs must still match the correct rows.

Worked example / Follow the trade-off, not just one number

Doubling our hypothetical vocabulary to 128,000 at fixed d and b doubles the input table to 524,288,000 bytes, or 500 MiB. An independent output weight table of the same shape would add another 500 MiB; tied weights would not. Meanwhile, a particular document might use fewer tokens, but doubling the vocabulary does not guarantee halving its sequence length. Additional entries help only when the encoding uses them.

LLM connection. A compatible tokenizer artifact, model weights, output mapping, and chat template form one contract. Swapping the tokenizer can select the wrong rows even when every ID is in range. Adding a token during fine-tuning requires corresponding model row allocation and learning, not just editing a text file. Positional information is also needed: architectures may add position vectors or use mechanisms such as rotary position transformations. A full treatment of these mechanisms is deferred; a token ID alone does not encode position.

Predict / Twice the rows, twice the width

If both V and d double with bytes per value fixed, how does table memory change? Why does a new ID not come with a useful learned vector automatically?

Reveal solution

The count becomes (2V)(2d)=4Vd, so memory quadruples. A new row needs initialization and suitable training; assigning an identifier does not supply learned behavior or preserve the model's output contract.

9. Special tokens, padding, chat, and tool handoffs

Ordinary pieces encode text content. Special tokens are designated vocabulary entries that a format uses for structure or a training task. Their human-readable spellings are not universal. A model may omit a category, reuse an ID for multiple purposes with configuration, or distinguish more boundaries than a simple tutorial shows.

Padding gives a rectangular representation

A batch groups examples processed together. A simple array operation expects a rectangle, with the same number of columns in every row. If token sequences have lengths 3 and 5, extend the first by two padding positions to make a two-by-five array. The attention mask identifies usable positions. In this example 1 means real input and 0 means padding; other interfaces can use different conventions.

Worked example / Padding overhead

The rectangle contains 2(5)=10 positions, but only 3+5=8 are real. Two positions are padding: 2/10=0.2=20\% of the allocated positions. Attention is the model operation that lets one position combine information from other positions; this mask tells it not to read padding positions as content. Training also needs appropriate target/loss masking, excluding padding from the prediction errors used to learn, so padding does not become an ordinary prediction target. The input attention mask and loss mask have different responsibilities.

Padding is only one visibility rule. A causal language model also blocks later positions: each position can use itself and the permitted earlier positions, not future tokens. The choice of left or right padding and the handling of position indices depend on the implementation. Some systems pack examples together or use operations for variable-length inputs to reduce wasted work. Follow the model's settings rather than copying this toy's convention.

A chat template turns application objects into model input

Your application may store {"role":"user","content":"Hello"}. That object is not automatically the token sequence the model was trained to receive. A chat template serializes messages, meaning it arranges their roles, boundaries, content, and optional generation prefix into the expected representation. Some APIs perform this step for you; other runtimes require you to apply the model's own template.

Conceptual serialization only, not a real model format:
[MESSAGE_START]user[CONTENT]Hello[MESSAGE_END]
[MESSAGE_START]assistant[CONTENT]

The unfinished assistant prefix cues generation in this toy format. Bracketed labels above stand for hypothetical structural IDs, not instructions to type those strings into any API. Role names may be ordinary text in one format and encoded differently in another. A literal marker-like string inside untrusted user text must not be blindly promoted into a privileged structural token. Use the supported template and special-token policy rather than concatenating unescaped content into your own invented control format.

Worked example / Count structure as well as content

Suppose a hypothetical completed message uses one start ID, one role ID, one content-boundary ID, two ordinary content tokens, and one message-end ID. Its length is 1+1+1+2+1=6 tokens, not two. Two such messages need 12 positions before any assistant-generation prefix. This is explicit toy arithmetic; real role names, headers, tool definitions, and content can require different counts.

Message end, turn end, and handoff are different events

A message end finishes one message record. An assistant-turn end says the assistant is done for now. A handoff yields control to a tool or runtime. Some formats distinguish all three with separate markers; others encode them differently. Treating every message terminator as a final answer can break a tool loop, and treating a handoff as permission can be unsafe.

For example, the model may generate a request for get_weather with {"city":"Bengaluru"}. The runtime first recognizes the request, checks its arguments and permissions, then calls the tool. It returns either the result or an error as a tool message. A later model pass can use that message to answer. Generating a control marker does not itself make an HTTP call.

Implementations represent tool requests in different ways. Some use special tokens; others use structured text or constrained decoding, which restricts the allowed generated continuations. Some combine these methods. Tool calling is not universally one special token.

LLM connection. Chat structure helps a trained model distinguish message sources, but does not guarantee instruction hierarchy or prompt-injection resistance. Keep role boundaries, untrusted content, permission checks, and execution policy separate. Tokenization is a representation layer, not a security boundary by itself.

Predict / A half-finished tool loop

The assistant emits a well-formed tool request. Is the task complete? Should an application execute it just because the JSON parses?

Reveal solution

No. The runtime still needs validation and authorization, actual execution or an explicit error, a returned tool result, and often another model generation. Syntactic validity does not establish safety, permission, or success. Preserve the format's handoff versus turn-end distinction.

10. Budget tokens, not words or permanent memory

A context window limits how many tokens a model can work with in the current request. It is not a permanent archive. A database or conversation store can keep more information outside the model. The application must choose which parts to retrieve and include in the current request.

First check what your model and API count. Our example assumes one shared limit for input plus generated output. Under that rule, reserve output space before filling the input. A separate maximum-output limit may apply too.

Counting only the message text can miss chat-template markers, tool definitions, images, audio, or other inputs the provider counts. Use the supported counting method for the complete request.

R=C-(I+H+D+T+O)

C is shared context capacity in tokens. I is instructions and serialization overhead; H is selected history; D is retrieved document text; T is tool-result text; O is reserved output. R is remaining headroom. The plus signs add categories that must not double-count the same token; subtract the entire grouped total from capacity.

Worked example / A request that fits, then one that does not

Let C = 16,000, I = 1,000, H = 2,000, D = 7,000, T = 1,000, and O = 3,000. First sum actual input allocations:

1{,}000+2{,}000+7{,}000+1{,}000=11{,}000

Add output reserve to get 14,000. Remaining headroom is 16{,}000-14{,}000=2{,}000.

A new 2,500-token tool result raises input to 13,500. With the same output reserve, total planned use becomes 16,500, exceeding capacity by 500. The application must reduce input, reduce the permitted output where appropriate, use another compatible capacity, or explicitly fail. It should not silently claim that the model remembered text it discarded.

If the request is too large, the system may reject it or follow a configured policy: trim history, summarize it, or retrieve fewer passages. Make that policy explicit. A summary can lose details. Cutting an ID list at an arbitrary point can break a message boundary or a byte sequence. Prefer complete sentences, messages, or code blocks where possible, keep required structural tokens, and check the assembled request again.

Retrieval chunks and overlap

Retrieval-augmented generation, abbreviated RAG, supplies selected external text as context. A chunk is one retrievable segment. Overlap repeats part of one chunk at the start of the next to preserve local context, but repeated text uses budget again when both chunks are sent.

Worked example / Chunk count and duplicate tokens

For an illustrative document of exactly 1,250 tokens under one fixed tokenizer, choose chunk size 500 and overlap 50. The stride, how far the start advances, is 500-50=450. Using one-based inclusive positions, chunks are 1-500 (500 tokens), 451-950 (500), and 901-1,250 (350). Each length is last position minus first plus one: 1{,}250-901+1=350.

Sending all three repeats 50 tokens twice:

500+500+350=1{,}350=1{,}250+100

This excludes chunk labels and template overhead. Token-based windows make capacity more predictable, but still prefer sentence/code boundaries, avoid broken Unicode when decoding slices, and recount the final serialization. Retrieval's tokenizer can differ from generation's; measure the generator's actual request.

Cost is a weighted count with units

Some APIs price input and output separately, sometimes also distinguishing cached or other usage categories. A rate is currency per token quantity; multiply matching units and add categories. The following prices are invented teaching rates, not a provider quotation.

K=\frac{n_{\mathrm{in}}}{10^6}r_{\mathrm{in}}+\frac{n_{\mathrm{out}}}{10^6}r_{\mathrm{out}}

K is total currency cost; n with subscript "in" or "out" is the actual token usage in that category. Each r is currency per million tokens, and 10^6=1{,}000{,}000. Division converts token counts to millions before multiplying by the rate. Reserved maximum output is not the same as actual billed output.

Worked example / One request and a repeated workload

At hypothetical rates of $2 per million input tokens and $6 per million output tokens, 11,000 input and 1,200 actual output cost (11{,}000/1{,}000{,}000)(2)=\$0.022 and (1{,}200/1{,}000{,}000)(6)=\$0.0072. Add them to get $0.0292 per request. At 1,000 identical requests without other billing categories, that is $29.20. Reserving 3,000 output positions in the earlier example does not mean billing 3,000 output tokens here.

LLM connection. A serving system first processes the supplied input, often called prefill, then generates additional tokens. It may keep a cache of intermediate model calculations to avoid repeating work. More tokens often mean more input work, cached data, and generation steps, but token count alone is not a universal latency formula. Architecture, batching, caching, hardware, and serving policies matter. A compact tokenizer is useful only as part of a compatible, measured system.

Predict / Why the same document can fit yesterday and fail today

You switch the generation model but keep a document's old "500-token" chunk label. Is it still a 500-token chunk? Does a long context mean the model retains it tomorrow?

Reveal solution

Not necessarily. The new tokenizer and serialization can produce another count; recount using the new compatible artifact. A context window holds current inference information, not persistent application storage. Tomorrow's request must explicitly retrieve or resend whatever is needed.

Optional local experiment: one named byte-BPE encoding

The Python example uses cl100k_base, a specific historical encoding name supported by tiktoken, not a synonym for all current GPT tokenizers. It deliberately publishes no claimed counts. The first run may download public encoding data; the text is encoded locally. Install tiktoken in an isolated Python environment if you choose to run it. from importlib.metadata import version
import tiktoken

enc = tiktoken.get_encoding("cl100k_base")
print("package", version("tiktoken"), "encoding", enc.name)
samples = [
    "map", " map", "getMap", "get_map",
    '{"enabled":true}', '{\n  "enabled": true\n}',
    "caf\u00e9", "cafe\u0301",
    "\u4f60\u597d", "\u3053\u3093\u306b\u3061\u306f",
    "\u0928\u092e\u0938\u094d\u0924\u0947",
]

12. Work it through and explain it aloud

Use these questions for practice or interview preparation. Explain what happens, why it happens, and where the explanation stops applying. An algorithm name alone is not enough.

01 / Rebuild one BPE state

With the weighted corpus from section 3, stop after rank 1. List all pair counts and predict rank 2. What is the vocabulary size after that second merge?

Reveal solution

The sequences are ma p (4), ma p s (2), and ma p l e (1). Counts are (ma,p):7, (p,s):2, (p,l):1, and (l,e):1. Merge ma with p. Six initial entries plus two new ones gives eight; the old m, a, and p entries are retained.

02 / Unknown word versus unknown base unit

Use the rank-2 toy tokenizer to encode maples. Why can you not promise the same for mapped? How would complete byte coverage change that answer?

Reveal solution

maples becomes map | l | e | s, IDs [7,4,5,3]. The toy lacks d, so mapped requires rejection or an explicit fallback. A complete byte base can represent its UTF-8 bytes without learning a new whole-word entry. That does not guarantee the model understands the word or that the count is small.

03 / Trace a greedy failure

Use start entries a, ab and only continuation ##bc. Why can greedy WordPiece fail on abc when a valid segmentation exists?

Reveal solution

It commits to the longest beginning ab, then cannot represent the final c. A backtracking search could choose a | ##bc; this greedy procedure does not. In the declared whole-word unknown policy it returns UNK. A set of available pieces and an encoding algorithm are both necessary to predict behavior.

04 / Best path is not total likelihood

For the Unigram toy, encode ab and compute its summed likelihood. If ab is removed while original scores are frozen, which path survives?

Reveal solution

The whole token ab scores 0.2. The split a,b scores 0.4(0.3)=0.12. Best-path decoding selects ab, while summed likelihood is 0.2+0.12=0.32. Removing ab leaves the split with score 0.12. Frozen scores illustrate removal impact; a trained pruned model must re-estimate token probabilities.

05 / Calculate model storage

A hypothetical input embedding has 50,000 rows, 768 columns, and 2-byte values. Calculate parameters and decimal MB. Would using the same tokenizer for a second unrelated model be safe?

Reveal solution

50{,}000(768)=38{,}400{,}000 parameters. At two bytes each, memory is 76,800,000 bytes, or 76.8 MB for that table alone. Shared dimensions do not prove shared row meanings: the second model needs its compatible vocabulary mapping and format. The same ID can select entirely different learned content.

06 / Padding and structural cost

Three sequences have lengths 2, 4, and 5. Right-pad to the longest. How many positions are padding, and what fraction of the rectangle is that? Is PAD necessarily the same ID as EOS?

Reveal solution

The rectangle has 3(5)=15 positions and 2+4+5=11 real tokens. Padding uses 3+1+0=4 positions, or 4/15\approx26.67\%. Their masks end in three, one, and zero zeros respectively. PAD and EOS have different conceptual jobs; some configurations reuse an ID with masks, but never assume that without checking.

07 / Design a budget failure policy

A 16,000-token service has 13,500 input tokens and a requested output allowance of 3,000. Explain what you would change, what you would recount, and why "persistent memory" does not solve the immediate overflow.

Reasoned solution

Planned use is 16,500, so remove at least 500 tokens or reduce output by at least 500 if the task and provider permit; practical headroom may call for more. Prefer reducing low-priority retrieval/history at safe boundaries. Re-serialize and recount instructions, template, schemas, selected content, and output allowance. External memory stores omitted information but does not make it available in the current inference unless it is retrieved into the bounded context.

08 / Explain the complete path without jargon

Explain how text reaches a model, compare the three algorithms, and follow a tool call back to an answer. Include why whitespace, language, and model compatibility matter.

Guidance for your explanation

A configured tokenizer transforms text, segments it with an existing vocabulary, and maps pieces to IDs. BPE learns merges; WordPiece uses a useful subword vocabulary with commonly greedy encoding; Unigram estimates and prunes pieces while considering alternative paths. A framework such as SentencePiece can supply more than one algorithm. IDs select learned embedding rows rather than measuring meaning. Whitespace, scripts, and code patterns alter available pieces and counts. A compatible chat format includes role and boundary information. A generated tool request must be validated and executed by the runtime, with a result supplied to a later model pass. Budget the actual compatible tokenized request, not words or another model's counts.

13. The boundary between strings and numerical models

Keep these connections

Represent. Segment. Identify. Look up.

  • Visible characters, code points, bytes, words, and tokens count different things.
  • Training constructs a tokenizer; encoding uses it; model training learns numerical parameters.
  • BPE merge ranks, WordPiece greedy matching, and Unigram path scoring are different procedures.
  • Complete byte coverage prevents missing base bytes, not missing knowledge or uneven efficiency.
  • Vocabulary size affects embedding storage and output classes as well as sequence lengths.
  • Special tokens and templates express structure; the runtime owns tool execution and authorization.
  • Measure the actual model-compatible request, including overhead, output allowance, and repeated retrieval text.
