From Text to Tokens: How LLMs Read Language

Follow a message from characters to vocabulary entries, then calculate what those choices cost in context, memory, and engineering complexity.

Prerequisite: basic arithmetic; chapters 01-02 provide connections13 sectionsOriginal diagrams + fully worked algorithms

The question we are answering

Your application sends a short message, yet the API reports many tokens. What exactly did the model receive, and why does the answer depend on the tokenizer?

A text box accepts a string. A language model works with numerical arrays. Between those two interfaces sits a tokenizer: a configured procedure that represents text as a sequence of vocabulary identifiers. It does not first understand the sentence and then choose its meaning. It follows rules about text and available pieces.

The word "read" in this chapter's title means this input conversion, not human comprehension. We will build small tokenizers you can trace with a pencil, distinguish their assumptions from real implementations, and connect their output to the matrices and learning machinery of the earlier chapters. No probability or Unicode knowledge is assumed.

How to work through this chapter

First learn the units and lookup contract in sections 1-2, then trace the three algorithms in sections 3-7. Sections 8-11 connect them to model storage and application requests. In section 6, understand the three-path example before continuing into the more demanding dynamic-programming, logarithm, and estimation calculations; they explain implementation choices, not prerequisites for recognizing a token. Each section has an explained check so you can test your reasoning before moving on.

1. Text, characters, bytes, and tokens are different units

Imagine storing the customer message Send maps.. A word is a linguistic unit; spaces and punctuation help a human recognize words in this English example. But spaces are not universal word boundaries. Chinese text, source code, email addresses, and product identifiers all challenge a simple "split on spaces" rule.

A character is an ambiguous term in software. A user-perceived character, also called a grapheme cluster, can contain several underlying pieces. Unicode assigns numbered code points to text elements. The notation U+0041 names the code point for capital A; the part after U+ uses base sixteen, whose digits continue after 9 with A through F. A code point is not itself a byte.

A bit has two possible values, 0 or 1. A byte contains eight bits. A positive integer exponent means repeated multiplication: 282^828 means eight factors of 2. Eight binary choices give 28=2×2×2×2×2×2×2×2=2562^8=2\times2\times2\times2\times2\times2\times2\times2=25628=2×2×2×2×2×2×2×2=256 possible patterns, conventionally numbered 0 through 255. A text encoding maps code points to byte sequences. UTF-8 represents each permitted Unicode code point with one to four bytes. Unicode reserves a range of numbers called surrogates for UTF-16's internal encoding machinery; they are not independently encodable text characters in valid UTF-8.

For example, Unicode NFC normalization combines this e-plus-accent into the precomposed form. A tokenizer may normalize, lowercase, or preserve text; its configuration decides. Worked example / Count the unit you mean

For Aé using precomposed é, there are two code points and 1+2=31+2=31+2=3 UTF-8 bytes: [65, 195, 169]. A raw byte tokenizer would emit three ordinary tokens. A toy vocabulary containing the entire byte sequence for Aé could instead emit one token. Neither count is a count of English words. In JavaScript, string.length counts UTF-16 code units, another storage unit; do not assume it counts graphemes, Unicode code points, UTF-8 bytes, or model tokens.

A token is one unit recognized by a particular tokenizer. Ordinary text tokens can cover a whole word, part of a word, punctuation, whitespace, or several of these together. Byte tokens can even cover less than a complete Unicode character. Special tokens, introduced in section 9, represent structure rather than ordinary text.

Predict / Same appearance, same count?

Without normalization, must the two accent spellings above produce the same tokens? What changes if both are normalized to NFC first?

Reveal solution

No. Their byte inputs differ, so a byte-based tokenizer can produce different IDs and counts. NFC makes these particular inputs identical before segmentation, so a deterministic tokenizer with the same configuration then produces the same result. Decoding cannot tell which original spelling was used after that distinction has been removed.

2. A vocabulary is a contract, not a dictionary of meanings

A vocabulary is the finite collection of token entries available to the tokenizer. A token ID is an integer identifying one entry. A sequence is an ordered list: [7, 3] is different from [3, 7]. Order matters because map followed by s spells something different from s followed by map.

Segmentation means choosing the ordered pieces that cover an input. In our displays, map | s means two tokens, not text containing a vertical bar or an inserted space. Similarly, m a p shows three character tokens from map; the separating spaces are diagram notation. Literal spaces in input will be called out explicitly. A saved tokenizer artifact contains its vocabulary and the rules and settings needed to repeat its behavior.

With the segmentation ["map", "s"], encoding maps maps to [7, 3]. Decoding looks up the entries and reconstructs maps. ID 7 is not seven units of meaning. Its distance from ID 3 does not measure similarity. Renumbering this vocabulary is safe only if all dependent model rows, output classes, and special-token settings are updated consistently.

An embedding is an ordered list of learned numerical values associated with a token, also called a vector. An embedding matrix is the rectangular table of these lists, with one row per ID and one column per value. A model parameter or weight is an adjustable stored number; training changes such numbers. The Transformer is the neural part of the model that processes these vectors. Its internal architecture is not needed to perform the lookup below.

Why not store every word? A word-only dictionary must handle new names, typos, code, and word variations; an unseen word may become an out-of-vocabulary item, abbreviated OOV. A character-level system reuses smaller pieces but usually needs longer sequences, and a finite character inventory can still miss a character. A subword system reuses pieces smaller than words while retaining larger common units. A piece is not guaranteed to be a grammatical root or suffix.

A compiler lexer is a useful analogy: both turn text into units. But a programming-language lexer recognizes a specified grammar, whereas many LLM tokenizers learn reusable units from a corpus, a collection of training text. Neither operation alone is semantic understanding.

Do not confuse three different activities

Tokenizer training constructs a vocabulary and its segmentation settings from a corpus. Encoding and decoding use that already-built artifact; they normally do not update it when a user sends a message. Model training adjusts neural parameters, including embedding values, to improve predictions on token sequences. In ordinary generation, both tokenizer configuration and model weights stay fixed while new output tokens are chosen.

Worked example / The simplest lookup into a model

Suppose a toy embedding table has eight rows, one per ID above, and three numbers per row. The sequence [7, 3] selects row 7, [0.2, -0.5, 0.8], followed by row 3, [0.6, 0.1, -0.2]. The resulting input has two rows and three columns. You do not multiply all numbers by 7 or 3. Chapter 1's matrix operations act on the retrieved values; chapter 2's training updates those values.

Tokenizer decoding does not itself generate a reply. During inference, using a trained model rather than updating its weights, an application supplies IDs and the model predicts possible next IDs. A generation procedure chooses an ID and repeats with the extended sequence. If a toy generation chooses ID 7 and then ID 3, the tokenizer can decode those chosen IDs as maps; it did not decide which IDs to choose. Serving documentation sometimes calls the iterative generation phase "decode" too. Check which of these two meanings is intended.

Predict / New spelling or new training?

The tokenizer has map, l, and e but no whole maple entry. Must an application train a new tokenizer to encode it?

Reveal solution

No, provided its encoding rules can produce map | l | e. Whole-word novelty does not imply failure when the underlying pieces exist. This says nothing about an unseen character outside the base vocabulary; that needs a defined fallback or an explicit failure.

3. BPE training: count, merge, recount

Imagine a log compressor that repeatedly notices the same adjacent fragments. Replacing two fragments with one saves one sequence position at each non-overlapping occurrence. Byte Pair Encoding, or BPE, began as a compression method; tokenizer training adapts the pair-merging idea to build reusable units. Despite the historical name, our first example starts with characters, not bytes.

Adjacent means immediately next to each other in the current sequence. A pair's frequency is its occurrence count, including repeated corpus entries. A merge replaces a selected adjacent pair with one combined token. The new entry is added to the vocabulary; old entries remain usable. A merge rank records its order in training, with a smaller rank meaning an earlier merge.

Exact assumptions for this teaching tokenizer

Our entire corpus is map four times, maps twice, and maple once. We process entries in that order. We start with the six characters m, a, p, s, l, e; there are no boundary tokens or special tokens. Pairs never cross entry boundaries. On equal frequency, select the pair first encountered while scanning these entries from left to right. Replace non-overlapping occurrences from left to right. Stop after five merges. These deterministic rules make this example reproducible; they are not a specification for every BPE library.

We can store each unique entry once with its frequency. This is equivalent to repeating it in the corpus. To count a pair, count occurrences within each entry, multiply by that entry's frequency, and add. For example, (m,a) appears once in each entry, so its total is 1(4)+1(2)+1(1)=71(4)+1(2)+1(1)=71(4)+1(2)+1(1)=7. The parentheses here group arithmetic factors; in (m,a) they denote an ordered pair of tokens.

Worked example / Every merge and every intermediate corpus

Rank 1. The top count 7 is tied. Our scan sees (m,a) first, so merge it into ma. The entries become ma p (4), ma p s (2), and ma p l e (1). Recount: (ma,p):7, (p,s):2, (p,l):1, (l,e):1.

Rank 2. Merge (ma,p) into map. The entries become map (4), map s (2), and map l e (1). Recount: (map,s):2, (map,l):1, (l,e):1. A one-token entry has no adjacent pairs.

Rank 3. Merge (map,s) into maps. The entries become map (4), maps (2), and map l e (1). Recount: (map,l):1, (l,e):1.

Rank 4. The counts tie again; our scan reaches (map,l) first. Merge it into mapl. The entries become map (4), maps (2), and mapl e (1). Only (mapl,e):1 remains.

Rank 5. Merge (mapl,e) into maple. The entries become map (4), maps (2), and maple (1). No pair remains. We reached the merge limit and would also stop because no further merge is possible.

Overlaps make "count" different from "replace"

For a a a, the pair (a,a) occurs at positions 1-2 and 2-3, so its adjacent-pair count is 2. But replacing the first pair consumes the middle a. A left-to-right non-overlapping replacement yields aa a, not two aa tokens. That is one actual replacement and one position saved. Libraries can differ in training details; do not assume pair count always equals immediate token savings when pairs overlap.

LLM connection. Production tokenizer training uses vastly larger corpora, targets, and implementation machinery. The enduring mechanism is to count the current units, add a merged entry, and update the representation. A vocabulary target must leave room for base and special entries; training may stop early if no useful pair remains.

Predict / A tempting but wrong recount

Immediately after rank 2, should (a,p) still have count 7? What happens if the frequency of maps rises from 2 to 5?

Reveal solution

No. The current sequences contain map, not separate a and p tokens. Its old pair is no longer adjacent in the representation. With maps frequency 5, the first two winning pairs each count 4+5+1=104+5+1=104+5+1=10. After those merges, (map,s) counts 5 and still wins rank 3. Counts describe the corpus supplied, not a timeless property of a word.

4. BPE encoding, byte coverage, and decoding

Training writes the dictionary and merge ranks. Encoding reads them. It does not recount a user's message to discover a new vocabulary. For our toy encoder, split an input entry into base characters, find adjacent pairs that occur in the learned merge list, apply the eligible pair with the smallest rank, and repeat until none applies. Resolve repeated occurrences with the same left-to-right replacement rule used above.

Worked example / Encode using a frozen prefix of the training

Freeze training after rank 2. The available merges are m + a -> ma (rank 1) and ma + p -> map (rank 2). Encoding the previously unseen entry maples follows m a p l e s -> ma p l e s -> map l e s. No listed pair remains. Using section 2's vocabulary, the IDs are [7, 4, 5, 3].

Decode by lookup: ID 7 gives map, 4 gives l, 5 gives e, and 3 gives s. Concatenation, joining without inserting extra text, yields maples. It is a new complete word composed from old entries. If instead we use the final five-merge tokenizer, the same input ends as maple | s. Changing the tokenizer artifact changes the result.

Merge-rank BPE is not generally interchangeable with "take the longest string in the vocabulary." Greedy longest-match is a different encoding rule, used in the WordPiece example below. Record the algorithm as well as the vocabulary. Preprocessing, boundaries, and rank order are all part of a reproducible BPE encoding.

Worked example / Two eligible merges compete

Use a separate toy vocabulary {a, b, c, bc, ab}. Its learned rules are b + c -> bc at rank 1 and a + b -> ab at rank 2. Such rules can result, for example, from a corpus containing bc three times and ab twice. Encode the new input abc, initially a b c.

Both (a,b) and (b,c) are eligible, but rank 1 wins even though its pair is farther right. The sequence becomes a bc. No rule merges a with bc, so the final result is a | bc. Taking the longest vocabulary prefix instead would choose ab and leave c: ab | c. Both spell the input, but only the first follows these BPE ranks. Merge priority, not the current prompt's pair frequency or a leftmost-longest guess, decides this result.

What if a base unit is missing?

The six-character toy cannot losslessly encode mapped: d is missing. It must reject that input or follow an explicit unknown-unit policy. It would be wrong to silently invent d, a new ID, or a new merge. The same issue affects an alphabet trained without a newly encountered script.

Byte-level BPE begins with all 256 byte values, then learns merges over byte sequences. With that complete base vocabulary, any byte sequence can be decomposed into available units, even if no larger learned token matches. UTF-8 gives ordinary valid Unicode text a byte representation. This solves base-byte coverage, not semantic comprehension or equal efficiency across languages.

Byte fallback is a related but distinct configuration: a tokenizer whose normal units are characters or subwords can fall back to byte entries for an uncovered portion. It must actually include and enable those entries. Not every Unigram or SentencePiece tokenizer does. An UNK token instead says "unknown"; once spelling is replaced with it, exact reconstruction is usually impossible.

Worked example / Reconstruct bytes before decoding text

Suppose a byte vocabulary emits separate byte tokens for precomposed é with payloads [195] and [169]. A payload is the byte content stored in an entry; these byte values are not necessarily its token ID. Concatenating the payloads gives [195, 169], a valid UTF-8 encoding of é. Neither byte alone is a complete UTF-8 character. Decoding them independently as text can produce an error or replacement character. During inspection, show raw bytes; during streaming, keep incomplete UTF-8 fragments buffered until the sequence is complete. A model can also generate a byte sequence that is not valid UTF-8, so the decoder's error policy matters.

The surrounding pipeline changes the legal merges

Pre-tokenization divides input into chunks before the subword algorithm runs. A regular expression, a pattern describing classes of text, might separate letter runs, digit runs, or punctuation. Some byte-BPE implementations use such patterns. If map and ! are placed in separate chunks, no BPE merge can cross that boundary even if the combined bytes appear elsewhere in a vocabulary. Other designs do not require word pre-tokenization.

A useful inspection order is: configured normalization, pre-tokenization if present, conversion to base units, segmentation, ID mapping, and special-token processing. Exact ordering and responsibility vary by implementation. For a lossless configuration, decoding encoded text should recover the original text. For a normalizing or unknown-replacing configuration, the round trip may only recover the transformed representation. Compare actual outputs rather than assuming reversibility.

Predict / Bytes versus understanding

A byte-level tokenizer can encode a new company name written in an unfamiliar script. Does this prove the model understands it? Does adding that name to one prompt add a permanent token?

Reveal solution

Neither. Byte coverage guarantees a representable input, not a learned meaning. It may require many fragmented tokens. Encoding one prompt uses the existing artifact and does not add vocabulary entries or train the model.

5. WordPiece: a vocabulary and a greedy search

BPE asks which adjacent pair is frequent. WordPiece, associated with BERT-style models, constructs a useful subword vocabulary under a likelihood-oriented view of the corpus. Before using that word, a probability is an amount between 0 and 1 assigned to an outcome; the probabilities of a complete set of mutually exclusive choices, alternatives that cannot both be selected in one choice, add to 1. A likelihood evaluates how much probability a configured model assigns to the training data actually observed. Higher likelihood means that model finds those observations less surprising; it does not mean greater semantic truth. Section 6 will calculate such quantities explicitly.

The exact original vocabulary-training procedure is not fully specified in the BERT paper. A likelihood description is a conceptual motivation, not a universal executable WordPiece training recipe. In particular, do not present one pair-scoring formula from a tutorial as the definitive original algorithm. The encoding behavior of a specified implementation is a separate question and can be traced exactly.

Common BERT-style WordPiece encoding works on a pre-tokenized word. At its beginning, find the longest vocabulary prefix matching the remaining text. Then use continuation entries for later pieces. A prefix is text at the beginning: play is a prefix of playing. Greedy means commit to the best local choice now, without exploring all later alternatives.

A complete toy WordPiece vocabulary for this example
Beginning entriesContinuation entriesFallback
p, pla, play##a, ##b, ##ing, ##er[UNK]

The literal characters ## are display notation on continuation entries, not text to insert into the user's word. Start entries and continuation entries are different vocabulary items. This toy has no automatic byte fallback, lowercasing, length limit, or additional preprocessing.

Worked example / Trace longest-match-first

Encode playing. Start by testing the whole remaining string playing, then successively shorter prefixes playin, playi, and play. The first vocabulary match is play; consume its four letters. The remaining text is ing. Because we are inside the word, test ##ing, which exists. The result is play | ##ing, not p | ....

For player, choose the same start play, then ##er. For playful, choose play, but no continuation matches the remaining ful. In this BERT-style whole-word fallback example the result is [UNK], not a fabricated ##ful, and not a successful prefix with the rest silently dropped.

To decode the toy result play | ##ing, retain play, remove the continuation display prefix from ##ing, and attach ing without a space: playing. A real tokenizer's decoder also handles pre-tokenization boundaries and punctuation rules; stripping every ## from arbitrary input is not a general decoder. An UNK replacement cannot recover the missing word.

Why greedy is not a global search

For a sharper counterexample, use a separate dictionary with start entries a, ab and continuation entries ##bc only. Input abc chooses ab, then fails because ##c is absent. A global search could find a | ##bc, but ordinary greedy longest-match-first does not backtrack to find it. Configuration-dependent unknown handling is therefore part of the algorithm's contract.

LLM connection. WordPiece continuation markers let related spellings reuse pieces, but they do not prove the model has learned morphology, the structure of how words are formed. BERT-style models also use different training tasks and special tokens from many generative models. You cannot replace one tokenizer with another merely because both split words.

Predict / What does the marker mean?

Can ##ing in our toy serve as the first token of input ing? Does a missing continuation imply the word is meaningless?

Reveal solution

No: the toy requires a beginning entry at the first position, and no ing start exists. The failure describes vocabulary coverage and search rules, not meaning. Another configuration could use different rules or fallback entries.

6. Unigram: compare complete segmentation paths

Suppose a piece of text has several valid spellings in your vocabulary. Rather than follow one merge history, you can score the alternatives. A Unigram language-model tokenizer gives each token a probability and models a segmentation's score by multiplying its token probabilities. "Unigram" means that within this segmentation model a token's probability does not depend on the previous token. This is a tokenizer model, not the contextual next-token predictor inside an LLM.

Probability, multiplication, and addition from scratch

A probability is a nonnegative amount of total mass assigned to an outcome. For a finite set of mutually exclusive choices, the probabilities add to 1. The value 0 means no mass and 1 means all of it. A percentage is that amount multiplied by 100: 0.4=40/100=40%0.4=40/100=40\%0.4=40/100=40%. We will use the complete toy vocabulary {a, b, ab, ba} with probabilities 0.4, 0.3, 0.2, and 0.1. Check: 0.4+0.3+0.2+0.1=10.4+0.3+0.2+0.1=10.4+0.3+0.2+0.1=1.

To understand multiplication, imagine 100 first choices, 20 of which choose ab. If 40% of those continue with a, that route has mass 0.2(0.4)=0.080.2(0.4)=0.080.2(0.4)=0.08, or 8 out of 100. This uses the toy model's independent token choices. We add, rather than multiply, mutually exclusive alternative routes: "route A or route B" combines their masses. Real languages do not have independent tokens; independence is an assumption of this segmentation score.

Avoid repeating the same search

For longer text, explicitly listing all paths is expensive. Dynamic programming stores answers for prefixes so later steps can reuse them. For the best path, store the best product reaching each character boundary; for total likelihood, store the sum of products reaching it. A boundary is a gap before or after a character, numbered by how many characters have been consumed. The empty prefix has score 1 because multiplying by 1 leaves the first token's score unchanged.

Repeatedly multiplying fractions makes numbers tiny: ten factors of 0.1 give 0.110=0.00000000010.1^{10}=0.00000000010.110=0.0000000001. Computers store numbers with finite precision, so long products may underflow, rounding to zero. A logarithm turns multiplication into addition. Vocabulary training: start large, estimate, prune

Unigram tokenizer training starts with many candidate pieces rather than BPE's small base. It estimates their probabilities from the corpus, evaluates how much candidates help the objective, the numerical criterion training tries to improve, removes a set of low-utility pieces, then re-estimates. For our worked bridge the criterion is higher summed text likelihood, equivalently lower negative log-likelihood. Training protects required coverage units according to configuration. A candidate's utility is not simply its length or its individual probability: alternatives can compensate when it is removed.

The estimation is often expectation-maximization-style, abbreviated EM: alternate between assigning fractional credit to possible hidden segmentations and improving the token probabilities from that credit. The text is observed, but its segmentation is hidden. "Expectation" here means a probability-weighted average, not a guess about the future.

7. SentencePiece is a framework, not a fourth algorithm

A framework is software that supplies surrounding capabilities and configurable implementations. SentencePiece supports, among other options, BPE and Unigram tokenization. Calling a tokenizer "SentencePiece" alone does not tell you which of those algorithms it uses, how it normalizes, whether byte fallback is enabled, or what special IDs mean.

SentencePiece can train from raw sentences without requiring a prior space-based word splitter. It commonly represents whitespace with the visible marker ▁ (U+2581). A displayed piece ▁map can represent a leading space followed by map, rather than a literal underline in the user's input. A configured dummy prefix may add an initial boundary marker, and normalization may affect repeated spaces. Inspect the artifact rather than claiming that this notation always preserves every original space byte-for-byte.

Worked example / Boundaries are data or configuration

In a toy whitespace-preserving display with no dummy prefix, map maps could be shown as map | ▁map | s. Decoding the middle piece contributes a space and map. If instead we split on spaces and discard them first, we lose the distinction between one space and two unless we record it elsewhere. For text without spaces, such as 你好, neither BPE nor Unigram inherently requires inserting an English-style word boundary. Their surrounding preprocessing decides where segmentation is allowed.

How training coverage changes the token count

A tokenizer can cover a writing system in bytes without having learned efficient larger pieces for it. If a spelling occurs often in the training corpus, its adjacent base units can get more chances to win BPE merges. The same mechanism applies to recurring letters, punctuation, indentation, and code fragments. Frequency is not a guarantee of one particular merge because other pairs compete and preprocessing can block them.

Worked example / Same text and byte coverage, different learned pieces

Compare two hypothetical byte-BPE artifacts, each with all 256 base byte entries, identical preprocessing, no normalization, and no special tokens added. For the input éé, UTF-8 gives [195, 169, 195, 169]. Artifact A has no applicable learned merge, so it emits four byte tokens. Artifact B has learned the single rule [195] + [169] -> [195,169]. It applies at both non-overlapping occurrences, producing two tokens with payload [195,169] each. Neither artifact has a whole-string éé merge.

Both decode to exactly the same two visible letters. B uses two rather than four tokens because its vocabulary contains a reusable byte sequence, not because UTF-8 changed or the model became more intelligent. These counts belong only to the declared toys. Across real languages and code workloads, measure representative data: training coverage can affect fragmentation, cost, and context consumption, but token efficiency alone cannot establish language understanding.

8. Vocabulary choices become model dimensions

A larger vocabulary offers more reusable large pieces, potentially shortening sequences. But every extra model vocabulary row requires values to store and learn. Think of a table with one row per ID and one column per feature. An embedding is the vector retrieved from a row; its dimension is the number of numerical entries in that vector, not the number of words it understands.

E∈RV×d,N=Vd,M=VdbE\in\mathbb{R}^{V\times d},\qquad N=Vd,\qquad M=VdbE∈RV×d,N=Vd,M=Vdb

E names the embedding matrix. The membership symbol means E is a matrix of real numbers; its shape is V rows by d columns. V is the model's vocabulary row count, including supported special entries; d is the positive embedding width. N is the number of stored parameters, one per table entry. b is bytes per parameter, and M is total bytes for this table alone. Symbols written next to each other mean multiplication: Vd means V times d, and Vdb multiplies by b as well. The multiplication sign in a shape says rows by columns.

Our mathematical token positions started at 1 in section 6. IDs in these toy tables start at 0. For a dense vocabulary of V rows, valid IDs run from 0 through V−1V-1V−1. The notation Ej,:E_{j,:}Ej,:​ means row j, where j is a valid token ID and the colon selects all columns. Some real artifacts have reserved or non-contiguous IDs; inspect the model's actual row allocation rather than inferring it from a count of displayed ordinary pieces.

A parameter is a stored model number. FP16 and BF16 are two floating-point storage formats commonly using two bytes per value; we use only that storage fact here. The output side also typically scores a class for each vocabulary entry. With hidden width d, an untied dense output projection has dVdVdV weight values, plus any configured bias. Worked example / Follow the trade-off, not just one number

Doubling our hypothetical vocabulary to 128,000 at fixed d and b doubles the input table to 524,288,000 bytes, or 500 MiB. Meanwhile, a particular document might use fewer tokens, but doubling the vocabulary does not guarantee halving its sequence length. Additional entries help only when the encoding uses them.

Adding a token during fine-tuning requires corresponding model row allocation and learning, not just editing a text file. Positional information is also needed: architectures may add position vectors or use mechanisms such as rotary position transformations. A full treatment of these mechanisms is deferred; a token ID alone does not encode position.

Ordinary pieces encode text content. Special tokens are designated vocabulary entries that a format uses for structure or a training task. Their human-readable spellings are not universal. A model may omit a category, reuse an ID for multiple purposes with configuration, or distinguish more boundaries than a simple tutorial shows.

A batch groups examples processed together. A simple array operation expects a rectangle, with the same number of columns in every row. If token sequences have lengths 3 and 5, extend the first by two padding positions to make a two-by-five array. The attention mask identifies usable positions. Worked example / Padding overhead

The rectangle contains 2(5)=102(5)=102(5)=10 positions, but only 3+5=83+5=83+5=8 are real. Two positions are padding: 2/10=0.2=20%2/10=0.2=20\%2/10=0.2=20% of the allocated positions. Attention is the model operation that lets one position combine information from other positions; this mask tells it not to read padding positions as content. This does not describe the entire attention mask: causal language models additionally restrict which earlier positions a token can see, and padding side and position handling are implementation-specific. Some systems pack examples or use variable-length kernels to reduce wasted work. Follow the model's padding and mask settings rather than copying the toy convention.

A chat template turns application objects into model input

Your application may store {"role":"user","content":"Hello"}. That object is not automatically the token sequence the model was trained to receive. A chat template serializes messages, meaning it arranges their roles, boundaries, content, and optional generation prefix into the expected representation. Some APIs perform this step for you; other runtimes require you to apply the model's own template.

Conceptual serialization only, not a real model format:
[MESSAGE_START]user[CONTENT]Hello[MESSAGE_END]
[MESSAGE_START]assistant[CONTENT]

The unfinished assistant prefix cues generation in this toy format. Bracketed labels above stand for hypothetical structural IDs, not instructions to type those strings into any API. Role names may be ordinary text in one format and encoded differently in another. A literal marker-like string inside untrusted user text must not be blindly promoted into a privileged structural token. Use the supported template and special-token policy rather than concatenating unescaped content into your own invented control format.

Worked example / Count structure as well as content

Suppose a hypothetical completed message uses one start ID, one role ID, one content-boundary ID, two ordinary content tokens, and one message-end ID. Its length is 1+1+1+2+1=61+1+1+2+1=61+1+1+2+1=6 tokens, not two. Two such messages need 12 positions before any assistant-generation prefix. This is explicit toy arithmetic; real role names, headers, tool definitions, and content can require different counts.

Message end, turn end, and handoff are different events

A message end finishes one message record. An assistant-turn end says the assistant is done for now. A handoff yields control to a tool or runtime. Some formats distinguish all three with separate markers; others encode them differently. Treating every message terminator as a final answer can break a tool loop, and treating a handoff as permission can be unsafe.

For example, the model may emit a structured request for get_weather with {"city":"Bengaluru"}. The runtime must recognize the format, validate the arguments, check authorization, execute the external operation, handle failures, and return a tool-result message. Only then can another model pass use the result. A control marker does not itself call an HTTP endpoint. Some systems use special tokens, some structured text and constrained decoding, meaning generation rules restrict which continuations are allowed, and some a combination; tool calling is not universally "one magic token."

LLM connection. Chat structure helps a trained model distinguish message sources, but does not guarantee instruction hierarchy or prompt-injection resistance. Keep role boundaries, untrusted content, permission checks, and execution policy separate. Tokenization is a representation layer, not a security boundary by itself.

10. Budget tokens, not words or permanent memory

A context window is the bounded tokenized information a model can consider in an inference context. It is not a permanent archive. A database or conversation store can retain more information externally; the application must choose what to retrieve and place back into the current context.

Context accounting depends on the model and serving API. For a hypothetical text-generation service that counts input plus generated output against one shared limit, reserve output space before assembling input. A separate maximum-output limit can also apply. Text token counts alone may omit template overhead, tool schemas, images, audio, or other provider-accounted inputs. Count with the supported interface for the actual request type.

R=C−(I+H+D+T+O)R=C-(I+H+D+T+O)R=C−(I+H+D+T+O)

C is shared context capacity in tokens. I is instructions and serialization overhead; H is selected history; D is retrieved document text; T is tool-result text; O is reserved output. R is remaining headroom. The plus signs add categories that must not double-count the same token; subtract the entire grouped total from capacity.

Worked example / A request that fits, then one that does not

A new 2,500-token tool result raises input to 13,500. With the same output reserve, total planned use becomes 16,500, exceeding capacity by 500. Exceeding context may cause rejection or a configured truncation, summarization, or retrieval-reduction strategy. Make that policy explicit. Summarization is not lossless compression, and truncating arbitrary token IDs can cut a message boundary or a byte sequence. Prefer semantic boundaries, preserve required structural tokens, and revalidate the final assembled request.

12. Work it through and explain it aloud

These questions revisit the source's developed interview themes in new examples. Give the mechanism and a caveat, not only an algorithm name.

01 / Rebuild one BPE state

With the weighted corpus from section 3, stop after rank 1. List all pair counts and predict rank 2. What is the vocabulary size after that second merge?

Reveal solution

The sequences are ma p (4), ma p s (2), and ma p l e (1). Counts are (ma,p):7, (p,s):2, (p,l):1, and (l,e):1. Merge ma with p. Six initial entries plus two new ones gives eight; the old m, a, and p entries are retained.

02 / Unknown word versus unknown base unit

Use the rank-2 toy tokenizer to encode maples. Why can you not promise the same for mapped? How would complete byte coverage change that answer?

Reveal solution

maples becomes map | l | e | s, IDs [7,4,5,3]. The toy lacks d, so mapped requires rejection or an explicit fallback. A complete byte base can represent its UTF-8 bytes without learning a new whole-word entry. That does not guarantee the model understands the word or that the count is small.

03 / Trace a greedy failure

Use start entries a, ab and only continuation ##bc. Why can greedy WordPiece fail on abc when a valid segmentation exists?

Reveal solution

It commits to the longest beginning ab, then cannot represent the final c. A backtracking search could choose a | ##bc; this greedy procedure does not. In the declared whole-word unknown policy it returns UNK. A set of available pieces and an encoding algorithm are both necessary to predict behavior.

04 / Best path is not total likelihood

For the Unigram toy, encode ab and compute its summed likelihood. If ab is removed while original scores are frozen, which path survives?

Reveal solution

The whole token ab scores 0.2. The split a,b scores 0.4(0.3)=0.120.4(0.3)=0.120.4(0.3)=0.12. Best-path decoding selects ab, while summed likelihood is 0.2+0.12=0.320.2+0.12=0.320.2+0.12=0.32. Removing ab leaves the split with score 0.12. Frozen scores illustrate removal impact; a trained pruned model must re-estimate token probabilities.

05 / Calculate model storage

A hypothetical input embedding has 50,000 rows, 768 columns, and 2-byte values. Calculate parameters and decimal MB. Would using the same tokenizer for a second unrelated model be safe?

Reveal solution

50,000(768)=38,400,00050{,}000(768)=38{,}400{,}00050,000(768)=38,400,000 parameters. At two bytes each, memory is 76,800,000 bytes, or 76.8 MB for that table alone. Shared dimensions do not prove shared row meanings: the second model needs its compatible vocabulary mapping and format. The same ID can select entirely different learned content.

06 / Padding and structural cost

Three sequences have lengths 2, 4, and 5. Right-pad to the longest. How many positions are padding, and what fraction of the rectangle is that? Is PAD necessarily the same ID as EOS?

Reveal solution

The rectangle has 3(5)=153(5)=153(5)=15 positions and 2+4+5=112+4+5=112+4+5=11 real tokens. Padding uses 3+1+0=43+1+0=43+1+0=4 positions, or 4/15≈26.67%4/15\approx26.67\%4/15≈26.67%. Their masks end in three, one, and zero zeros respectively. PAD and EOS have different conceptual jobs; some configurations reuse an ID with masks, but never assume that without checking.

07 / Design a budget failure policy

A 16,000-token service has 13,500 input tokens and a requested output allowance of 3,000. Explain what you would change, what you would recount, and why "persistent memory" does not solve the immediate overflow.

Reasoned solution

Planned use is 16,500, so remove at least 500 tokens or reduce output by at least 500 if the task and provider permit; practical headroom may call for more. Prefer reducing low-priority retrieval/history at safe boundaries. Re-serialize and recount instructions, template, schemas, selected content, and output allowance. External memory stores omitted information but does not make it available in the current inference unless it is retrieved into the bounded context.

08 / Explain the complete path without jargon

Explain how text reaches a model, compare the three algorithms, and follow a tool call back to an answer. Include why whitespace, language, and model compatibility matter.

Guidance for your explanation

A configured tokenizer transforms text, segments it with an existing vocabulary, and maps pieces to IDs. BPE learns merges; WordPiece uses a useful subword vocabulary with commonly greedy encoding; Unigram estimates and prunes pieces while considering alternative paths. A framework such as SentencePiece can supply more than one algorithm. IDs select learned embedding rows rather than measuring meaning. Whitespace, scripts, and code patterns alter available pieces and counts. A compatible chat format includes role and boundary information. A generated tool request must be validated and executed by the runtime, with a result supplied to a later model pass. Budget the actual compatible tokenized request, not words or another model's counts.

13. The boundary between strings and numerical models

Keep these connections

Represent. Segment. Identify. Look up.

  • Visible characters, code points, bytes, words, and tokens count different things.
  • Training constructs a tokenizer; encoding uses it; model training learns numerical parameters.
  • BPE merge ranks, WordPiece greedy matching, and Unigram path scoring are different procedures.
  • Complete byte coverage prevents missing base bytes, not missing knowledge or uneven efficiency.
  • Vocabulary size affects embedding storage and output classes as well as sequence lengths.
  • Special tokens and templates express structure; the runtime owns tool execution and authorization.
  • Measure the actual model-compatible request, including overhead, output allowance, and repeated retrieval text.
